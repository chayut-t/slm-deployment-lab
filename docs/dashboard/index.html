LEARN-00

The evidence contract

Deep study~3 min
Covers T00 + T01 · why a deployment claim needs a pinned revision behind it

In plain words: before measuring anything, the project decided what counts as evidence. A model name like "Qwen3-0.6B" is not an identity — the same name can point to different weights over time. So the lab pins one immutable model revision (an exact commit hash), one hash-verified environment, and wraps every produced file in a manifest that records where it came from. A storage preflight even refuses to write large files when the external drive is not what it claims to be.

Key ideas

  • A manifest field is either a claim, a measurement, or provenance — and you should be able to say which.
  • Pins prove the source is reproducible; they say nothing about whether any compiler accepts the model.
  • Refusing to run (the preflight) is a feature: it prevents silent corruption.
Why this matters for the NPU goal NPU results are extremely version-sensitive: compiler, runtime, and device firmware all change the numbers. An NPU expert's first reflex is "which exact versions produced this?" — this checkpoint installs that reflex.
LEARN-01

Agentic delivery

Review~2 min
Covers T03 + T04 · a task graph that survives losing the conversation

In plain words: the AI agent session doing the work is disposable; the repository is not. All coordination lives in a dependency-aware task graph (YAML), a status page that is generated from it (so it can never drift), one-writer-per-file-set rules, and a strict public/private split: the committed ai/ tree is public, the ignored .ai-local/ tree holds session IDs and raw output. Git hooks reject the common mistakes automatically.

Key ideas

  • "Completed" is a strong word here: dependencies done, outputs delivered, worklog published, changes integrated.
  • A new agent (or you, months later) can reconstruct who owns what from the repo alone.
Why this matters for the NPU goal Indirectly: it is what lets the Qualcomm work proceed across many sessions without losing evidence. Review-level attention is enough.
LEARN-02

Fixtures as a contract

Deep study~3 min
Covers T10 · frozen prompts, exact token IDs, and the limits of "same input"

In plain words: two runs are only comparable if they consumed the same tokens, not the same text — tokenizers can differ, chat templates can differ, and "a 512-token prompt" can mean different work on two machines. So the lab commits three layers: the authored text, the generated token-ID bundle, and the workload manifest, all chained by hashes. A canary (a tiny prompt with a known exact output) sits beside the benchmark workloads: it measures nothing, but instantly catches a broken backend.

Key ideas

  • Both text and token IDs are committed, because each alone proves too little.
  • Canary ≠ benchmark workload ≠ quality case — three different jobs.
  • Licensed datasets (WikiText-2, HellaSwag…) are named and pinned but never committed.
Why this matters for the NPU goal When your NPU output differs from the reference, the first question is "did it even receive the same tokens?" Frozen fixtures make that question answerable in seconds instead of days.
LEARN-03

Static graphs & the KV-cache contract

Deep study~4 min
Covers T11 + T12 · what a compiler-facing graph family has to promise · the most important checkpoint so far

In plain words: this is the heart of NPU deployment. An accelerator wants fixed tensor shapes it can plan memory for; autoregressive decoding wants a cache that grows one token at a time. The resolution: split generation into two frozen graphs — a prefill graph that processes the whole prompt once and fills the KV cache, and a decode graph that takes exactly one token plus the fixed-size cache and returns the next token plus the updated cache. The cache is a fixed-capacity buffer updated by index, never by concatenation. A deterministic PyTorch oracle (T11) defines correct output; the contract (T12) is validated against it before any exporter or compiler is involved.

Key ideas

  • Cache shape per layer: [1, 8, C, 128] — 8 physical K/V heads, not 16, because of GQA. That halves cache bytes: FP16 cache ≈ 112 MiB at context 1,024, ≈ 448 MiB at 4,096.
  • Cache capacity exceeds prompt length (160/576/1,152/4,224 for prompts of 128/512/1,024/4,096) so decoding has room to write.
  • "Byte-identical logits" certifies the math path — but not shapes-on-device, placement, or speed.
Why this matters for the NPU goal This is the Qualcomm skill. Hexagon/HTP compiles static graphs; every LLM-on-NPU deployment in industry uses exactly this prefill/decode split with an explicit cache contract. Know this cold — shapes, dtypes, and why each number is what it is.
LEARN-04

Benchmarking without false equivalence

Deep study~3 min
Covers T13 · where a timer starts, and what a median is allowed to claim

In plain words: most published inference numbers are incomparable for boring reasons: timers that never waited for the GPU to finish, warm-up folded into the measurement, a mean over a lopsided distribution, or mixing a single-graph latency with a full request round-trip. The frozen protocol names five timing classes and forbids averaging across them. Statistics policy: medians with bootstrap confidence intervals, raw samples kept, p90/p95 reported with dispersion.

Key ideas

  • On a GPU/NPU, synchronization is part of the timer — an unsynchronized TTFT measures only kernel launch.
  • Hosted-job turnaround (e.g. 45 s) and measured graph latency (e.g. 8 ms) are different classes; only one belongs in a benchmark table.
  • T13 produced no numbers — it is the rulebook later numbers are judged by.
Why this matters for the NPU goal AI Hub gives you single-graph profile latencies; Device Cloud gives you end-to-end loop timings. An NPU expert never confuses the two — this protocol is the discipline that keeps your Qualcomm claims honest and defensible.
LEARN-05

ONNX export as a compiler contract

Deep study~3 min
Covers T20 · eight graphs, four manifests, and one very narrow claim

In plain words: the T12 contract became eight real ONNX graphs — prefill + decode at each of the four context sizes. Model weights are forced into external data files (kept out of Git, hashed separately), every graph passes the ONNX checker and exact name/dtype/shape conformance, and each manifest re-hashes everything it asserts. The claim earned is deliberately small: the pinned toolchain produced valid graphs that match the contract. Nothing more.

Key ideas

  • Export success ≠ compiler acceptance ≠ NPU placement ≠ performance. Four separate hurdles.
  • The decode cache update is a dynamic index into a fixed-shape tensor — concatenation would break the static-shape promise.
  • A passing ONNX checker does not rule out an unsupported operator on the NPU.
Why this matters for the NPU goal ONNX is the doorway format into Qualcomm's toolchain. Knowing exactly what an export does and does not prove is what separates "it exported fine!" from an engineer who predicts where the QNN compiler will complain.
LEARN-06

The Qualcomm public pipeline

Hands-on + deep study~3 min
Covers T02 + T30 · authentication, a bounded toy lifecycle, and real NPU placement

In plain words: the first Qualcomm contact produced two things worth studying. First, a documented authentication failure — kept as a failure analysis with a safe credential procedure (the credential is never printed or logged). Second, one complete free compile → inference → profile lifecycle of a toy graph on a physical Snapdragon X Elite through AI Hub Workbench, with confirmed NPU placement. The T30 adapters wrap each stage so it can restart from a saved, content-addressed manifest rather than a live job handle, and so no job ID, URL, or credential can leak into a public file.

Key ideas

  • Service turnaround (queue + scheduling) is not device latency.
  • Unobserved values are recorded as null, never inferred — an "unknown" in a profile is honest data.
  • A toy proving the lifecycle says nothing about whether a 0.6B transformer compiles or places on the NPU.
Why this matters for the NPU goal This is your primary toolchain. The hands-on part (re-running the lifecycle with your own credentials) is worth doing once yourself — it burns the compile/infer/profile mental model in, and it is the exact loop T31 will run at Qwen scale.
LEARN-07

A real generation loop on a real device

Hands-on + deep study~3 min
Covers T32 · what a persistent device-side loop measures that a graph benchmark cannot

In plain words: a Workbench profile times one graph submission. A Device Cloud session runs a persistent generation loop on a physical Snapdragon and lets you separate every stage: artifact access, model load, tokenization, prefill, first decode, remaining decode, generation total, and full request wall time. The published single run (Qwen3-0.6B via Qualcomm's ready-made GenieX/llama.cpp route): prefill 69.9 ms, first decode 0.55 ms, remaining decode 292.8 ms, generation total 363.3 ms. It is published as one run — not a median — because one sample licenses no statistics.

Key ideas

  • Load and tokenization are excluded from decode throughput but included in request wall time — both are real, they answer different questions.
  • GenieX proves the device works; it proves nothing about this project's custom QNN graphs. That gap is exactly what T31–T33 must close.
  • Device identity evidence stayed private; only the sanitized latency aggregate was published.
Why this matters for the NPU goal End-to-end loops on real Snapdragon hardware are the deliverable of your target role. Knowing which timing boundary each number sits inside is what makes your device claims credible.
LEARN-08

Apple Silicon & MLX

Deep study~3 min
Covers T50 + T51 · from a packaged baseline to a runtime you wrote yourself

In plain words: first pin the packaged thing (MLX-LM as a versioned baseline on the M4, reproducing the oracle exactly, 38.3 tok/s on the smoke prompt), then replace it with your own runtime: explicit prefill and one-token decode, fixed-capacity FP16 caches in two layouts (head-major and sequence-major), and — the key move — handing the 8 physical K/V heads straight to MLX's grouped-query attention without ever tiling them to 16. The obvious implementation (repeat K/V to match query heads) doubles cache traffic and is simply wrong on a bandwidth-limited machine.

Key ideas

  • The same T12 cache contract drove a second, completely different backend — proof the contract is real, not ONNX-flavored.
  • MLX is lazy: without an explicit evaluation fence, your timer measures graph construction, not compute.
  • Fixed-capacity caches trade a little memory for zero reallocation on unified memory.
Why this matters for the NPU goal Cache layout, GQA-aware attention, and memory-bandwidth thinking transfer directly to Hexagon — the NPU is even more bandwidth- and layout-sensitive than the M4. This is the same problem in a friendlier gym.
LEARN-09

CI as a deployment surface

Hands-on + deep study~3 min
Covers T72 · a manually dispatched workflow that can touch a paid service

In plain words: the one place where a mistake costs money or leaks a token. A manual workflow_dispatch GitHub Actions workflow drives AI Hub with typed inputs (target device, context, precision, stage), behind layered defenses: an authorization job that refuses fork dispatches, a protected environment, minimal permissions, pinned actions, and a mode-600 ephemeral credential file (never an environment variable). One dispatch runs one stage — never the whole pipeline. Status: reviewed and offline-tested; no secret stored, nothing dispatched. The worklog's best part is the three rounds of security findings the first draft needed.

Key ideas

  • The GitHub runner is only an orchestrator — Qualcomm hardware runs the model.
  • Local scripts stay the implementation; the workflow is an operator surface over them.
  • Adding the secret and first dispatch are deliberately left to you (hands-on).
Why this matters for the NPU goal Real NPU teams run their compile/profile fleets through CI. Being able to build — and security-review — an automation layer over AI Hub is a differentiating, role-relevant skill.
LEARN-10

Reading a graph before a compiler does

Deep study~5 min
Covers T21 + T23 · what an exported graph tells you, and what only a measurement can

In plain words: T21 asked what a static-shape compiler will think of the exported graphs, and answered with a dependency-free protobuf reader (no torch, no onnx, no numpy). The findings, ranked by consequence for T22: 1,231 computed shape inputs (shapes recomputed at runtime even though every answer is a known constant), 56 scatter-based cache writes, a 37 MB per-token I/O boundary on the long-context decode graph, and a 33.5 MB causal mask baked into a single node. Then T23 actually ran the graphs, and the measurement taught two lessons. First, the prefill graphs could not even load: ONNX Runtime's CPU provider has no float16 Pad kernel and its automatic rewrite failed, so the cache write was re-exported as Concat — with the decode graphs and weights byte-identical. Second, the first real run missed the proposed tolerance — but a control showed the old tolerance also rejected float32 itself: a broken instrument, not a failing graph. It was re-derived from dtype ULP and 28-layer depth with no observed error used to set it (atol loosened, cosine tightened to 0.9993), and all four contexts now pass on real onnxruntime 1.28.0.

Key ideas

  • "Every dimension is static" and "compiler-friendly" are different claims — computed shapes must be folded to constants before QNN sees them.
  • A tolerance the reference dtype cannot pass is not evidence about a candidate. The control measurement is what separates re-deriving a threshold from widening it until green.
  • A cache-corruption bug can pass decode step one perfectly and only show at step three; that is why cache prefix checks are exact, never tolerant.
  • The measurement's scope is honest and narrow: one runtime build, one execution provider, one host, optimizations off — the paired ORT_ENABLE_ALL run is still untaken.
Why this matters for the NPU goal This is exactly the QNN discipline: predict where the compiler will complain, run the real thing, and when a number disagrees, question the instrument before blaming the graph. The findings list is literally the work order for T22 — the next task on the critical path — and the fixed export is the bytes T22 now builds from.
LEARN-11

Calibration data as a contract

Deep study~3 min
Covers T40 · freezing the inputs to quantization before quantizing anything

In plain words: post-training quantization reads activation ranges off a handful of sample inputs and turns them into scales and zero-points. Change the inputs and you change the deployed model. So the calibration corpus gets the same treatment the tokenizer got in T10: an exact revision, a frozen preprocessing rule, a hash that breaks if either moves, and a license trail. Two honest design calls stand out: short fixtures were tiled rather than padded to reach the fixed prefill length (padding would distort the activation statistics the quantizer learns from), and the coverage argument states exactly where it stops — the corpus touches only 175 of 151,936 embedding rows, and the docs say so instead of hiding it. The AIMET environment is pinned but honestly labeled: verified as a dependency resolution, not as a working installation.

Key ideas

  • No weight was quantized and AIMET never ran — this is a frozen input contract, not quantization evidence. T41 froze the W8A16/W8A8 candidate specs on top of it but produced no numbers either: it is blocked with no quantized artifact yet.
  • Calibrating and evaluating on the same four samples would flatter any quality delta; T41 has to report around that.
  • A parity gate can exit 0 with a verdict of partial — reading the scope field is part of reading the result.
Why this matters for the NPU goal Quantization is the deepest Qualcomm-specific skill in this project, and its most common failure mode in practice is sloppy calibration. Knowing why the corpus is a contract — and where its coverage argument stops — is what makes your W8/W4 claims in weeks 3–4 defensible.
LEARN-12

Rewriting a graph for a compiler you have not run

Deep study~4 min
Covers T22 · what a transformation catalogue can prove, and where the proof stops

In plain words: T21 ranked what was wrong with the eight reference graphs. T22 rewrites them and measures what changed. Six declarative passes — Constant-to-initializer, an allowlisted static shape fold, dead-node elimination, large-tensor externalization, shape inference, and a provenance stamp — cut prefill from 7,634 nodes to 2,785 and shrink the S4096 prefill protobuf from 49,790,614 to 958,654 bytes, collapsing a 9.70× size spread across the context matrix to 1.01×. The public boundary, the 56 cache writes, and the precision crossings stay exactly where the export put them. Then the candidates are executed through the unmodified T21 protocol and every logit comes back bit-identical to the reference.

Key ideas

  • A rewrite catalogue must be declarative, ordered, and target-neutral. Each pass cites the T21 finding it answers; a pass with no cited finding is a preference, not a fix.
  • Bit-identical logits are the expected result of a semantics-preserving catalogue — not a bonus. A one-ULP difference would have meant a pass changed the math.
  • The parity proof is non-circular by construction: each record's graph_digests names the candidate, not the reference, and the runner hard-fails on digest mismatch before a session exists.
  • A smaller finding count is not a more convertible graph. Every manifest's claim_boundary says so in-band, and lists compiler_acceptance among what it does not establish.
  • The trade is visible, not hidden. Folding shapes converts one risk class into another: decode's rank-1 R-DATA-DEPENDENT-SHAPE-INPUT falls 1,231 → 423, but 1,069 interior tensors whose shape inference cannot resolve appear as a new high-severity R-INTERNAL-DYNAMIC-SHAPE. By raw high-severity count decode gets worse. Prefill is the clean win (804 → 0 at S128, 804 → 6 at larger variants).
  • Judge an optimizer by the objective it was built for. ONNX Runtime's offline optimizer was rejected on four measured grounds — it decomposes all 28 Softmax nodes into five ops each, raises Cast from 348 to 830 (a CPU-provider float16 fallback, a host artifact irrelevant to a different target), stamps eight unused opset domains, and destroys the external-data layout by inlining weights back into a 1.81 GB protobuf, 84% of the 2 GiB ceiling.
Why this matters for the NPU goal This is the first task that rewrites a graph for a compiler rather than merely describing one. The discipline it models — every transformation recorded, reference and candidate kept distinct, and "ready for submission" defined narrowly enough to be honest before any service has been contacted — is what keeps a failed compile in T31 attributable. Because parity is bit-identical, any numerical divergence observed on a device is the compiler, the runtime, or the hardware; it is not these rewrites.

Glossary

The jargon used above, in one place.
SLM
Small Language Model — a compact LLM (here Qwen3-0.6B, 0.6 billion parameters) small enough to run on phones, laptops, and edge devices.
NPU
Neural Processing Unit — a chip block specialized for neural-network math at low power. On Snapdragon it is the Hexagon processor; its tensor engine is called HTP.
Hexagon / HTP
Qualcomm's NPU and its Tensor Processor. Runs compiled static graphs; the main deployment target of this project.
Snapdragon X Elite
Qualcomm's laptop chip and the project's primary device target. Dragonwing IQ-9075 (edge/IoT) and Snapdragon 8 Elite (mobile) are the comparison targets.
Prefill
The phase that processes the whole prompt in one pass and fills the KV cache. Compute-heavy.
Decode
The phase that generates one token at a time using the cache. Memory-bandwidth-heavy. Repeated once per output token.
KV cache
Stored Key/Value attention tensors for every past token, so each new token doesn't recompute the whole history. Its size and layout dominate LLM inference engineering.
GQA
Grouped-Query Attention — several query heads share one K/V head. Qwen3-0.6B has 16 query heads but only 8 K/V heads, halving cache size — if the runtime doesn't naively copy them back.
Static graph
A computation graph with all tensor shapes fixed at compile time. NPU compilers require this; it's why the prefill/decode split and fixed-capacity caches exist.
ONNX
An open interchange format for model graphs. The project's doorway from PyTorch into hardware toolchains.
External data (ONNX)
Model weights stored in files beside the graph instead of inside it — required for large models, hashed and transported separately.
ONNX Runtime (ORT)
Microsoft's engine that executes ONNX graphs on CPU, CUDA, and other backends. Used for CPU parity checks (T21) and the NVIDIA lane (T60).
QNN
Qualcomm's neural-network SDK/format family. A "QNN candidate" is a graph rewritten and packaged to be acceptable to Qualcomm's compiler.
Transformation pass
One recorded, rule-based rewrite of a graph (e.g. folding computed shapes into constants) that changes structure without changing the math. T22's catalogue applies six in a fixed order, each citing the finding it fixes.
AI Hub Workbench
Qualcomm's free public cloud service: upload a model, then quantize, compile, run inference, and profile it on real hosted devices.
Device Cloud
Qualcomm's service giving interactive sessions on real Snapdragon machines — used for the end-to-end generation loop, not just single-graph jobs.
GenieX
Qualcomm's ready-made on-device LLM runtime route (paired with llama.cpp). Used as a device baseline; it does not exercise the project's own graphs.
llama.cpp
A popular portable C/C++ LLM runtime. Powers the ready-made baseline route on Device Cloud.
Quantization
Storing weights/activations in fewer bits (8-bit, 4-bit) to shrink memory and speed up inference, at some quality cost. Core NPU skill.
W8A16 / W8A8 / W4A8
Quantization recipes: W = weight bits, A = activation bits. W4A8 = 4-bit weights, 8-bit activations.
Calibration
Running sample data through a model to choose good quantization scales. The calibration set is frozen in T40 so results are reproducible.
AIMET
Qualcomm's open-source quantization toolkit — simulation, calibration, and export of quantized models.
LPBQ
Low-Power Block Quantization — an AIMET technique using per-block scales to keep 4-bit weights accurate.
LiteMP
Mixed-precision quantization: keep sensitive layers in higher precision, quantize the rest harder, guided by sensitivity analysis.
Sensitivity analysis
Measuring how much each layer's quantization hurts output quality, to decide which layers deserve more bits.
MLX
Apple's array/ML framework for Apple Silicon. Lazy by default — work runs only when a result is forced, which matters for timing.
Unified memory
Apple Silicon design where CPU and GPU share one memory pool (M4: 16 GB at 120 GB/s). No copies between devices — bandwidth becomes the limit.
TTFT
Time To First Token — how long from request until the first output token. Dominated by prefill.
Canary
A tiny fixed prompt whose exact output (here token IDs 576, 8356, 3950) every backend must reproduce. A correctness tripwire, not a benchmark.
Fixture
Frozen test input — committed prompts and exact token IDs — so every platform measures identical work.
Manifest
A small JSON record attached to every artifact: hashes, versions, commands, and provenance. What makes a result reproducible and comparable.
Oracle
The deterministic pinned PyTorch reference (T11) that defines "correct output" for every other backend.
workflow_dispatch
A GitHub Actions trigger that runs a workflow only when a human presses "Run workflow" — used so cloud jobs can never fire by accident.
